# Widgets reliability research and implementation plan

Research date: 2026-11-17. Scope: repository review and external documentation/source review only. No source/config/runtime changes or tests performed.

## 1. Executive summary

The Widgets page is a real custom plugin system, not a front end to Windows' Widgets Board. It discovers DLLs from a `Widgets` directory, invokes a C ABI, measures and renders Direct2D content into DirectComposition surfaces, and positions visuals in an overlay tree shared with `icon_hover.dll`. Most likely reliability risks are: (1) the widget host depends on `icon_hover.dll` being loaded first and exporting a private bridge; `Enable` fails hard if this bridge is unavailable (runtime `widget_host_runtime.cpp:327-334,745-755`); (2) one taskbar HWND is captured at plugin initialization and subclassed, with no explicit taskbar/Explorer HWND reacquisition path after Explorer restarts (`:720-728,776-801`, message handling only removes the subclass at `:696-698`); and (3) plugins are arbitrary in-process DLLs, so SEH guards catch some structured exceptions but cannot isolate hangs, heap corruption, ABI mismatch, or C++ exceptions (`:85-153`). The committed log ends in September 2026 with core startup/shutdown only and no widget evidence (`Logs/taskbarengine.log:1-7`), so it does not identify the current runtime failure.

Recommendation: keep widget rendering out of Explorer and use a dedicated TaskbarEngine-owned host process/window for the long-term supported boundary, with versioned IPC and a stable widget protocol. The current overlay approach can be retained as a short-term compatibility path while its taskbar/overlay lifecycle and visibility are measured and repaired. If strict native taskbar embedding on Windows 11 is a hard requirement, treat it as OS-version-specific integration with explicit support limits: Microsoft has no documented general API for arbitrary app content embedded in the modern taskbar. Prefer an app-owned AppBar/taskbar-adjacent window for a supported alternative; it reserves screen space but is a separate bar/window. Windows Widgets APIs are not an alternative for this product surface.

## 2. Current code flow

1. GUI navigation adds a `Widgets` item tagged `widget_host` ([gui_main.cpp](../App/src/gui_main.cpp#L378)). Settings page gets schema/defaults and presents widget enable switches/order ([settings_page.cpp](../App/src/settings_page.cpp#L1631), [settings_page.cpp](../App/src/settings_page.cpp#L2142)).
2. Settings writes plugin-level `enabled` under `plugins.widget_host`; other flat keys are mapped into `widgets.*`, persisted, then GUI sends reload IPC ([settings_page.cpp](../App/src/settings_page.cpp#L89), [config_io.cpp](../App/src/config_io.cpp#L268)). `widget_host.cpp` subscribes to config-changed events and forwards updates to runtime ([widget_host.cpp](../Modules/widget_host/widget_host.cpp#L76)).
3. Plugin initialization stores `context->taskbar_hwnd`, derives `Widgets` path relative to its DLL, scans `*.dll`, loads each DLL, resolves `GetWidgetInterface`, checks required callbacks and metadata, then reads/duplicates widget config ([widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L157), [widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L278), [widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L720)). Build makes `clock.dll`, `sysmon.dll`, and `media.dll` and copies them under build `Widgets`; package/deploy copy that tree ([Modules/widget_host/CMakeLists.txt](../Modules/widget_host/CMakeLists.txt#L19), [Scripts/package.ps1](../Scripts/package.ps1#L67), [Scripts/deploy.ps1](../Scripts/deploy.ps1#L65)).
4. Enable resolves five private exports from already-loaded `icon_hover.dll`, acquires its DirectComposition resources, subclasses the captured taskbar window, starts a one-second timer and applies settings ([widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L327), [widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L745)). Each active widget is initialized/enabled, measured, given a DComp surface/visual, drawn with a borrowed D2D context and positioned in a shared visual tree. The timer redraws all widgets each second, including static content ([widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L416), [widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L535)).
5. Mouse messages are intercepted on the taskbar subclass and delegated to widget hit-test/click/scroll callbacks; drag reordering is written back to the config ([widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L520), [widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L611), [widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L490)). DPI/display/window-position messages call refresh. A graphics-generation change recreates widget surfaces ([widget_host_runtime.cpp](../Modules/widget_host/widget_host_runtime.cpp#L535)).

Configuration has a schema mismatch worth correcting: defaults store layout as JSON array `widgets.layout`, while GUI fallback schema, settings parser, and runtime `ParseLayout` expect a comma-separated string. The model parser's expected type should be verified at `widget_host_model.cpp:102`. This can cause default order to be ignored/fallback, and GUI order controls may not reflect saved config. Widget-level settings are in `widgets.clock/sysmon/media`; plugin enable remains `plugins.widget_host.enabled` ([default_config.jsonc](../Config/default_config.jsonc#L8), [default_config.jsonc](../Config/default_config.jsonc#L51)).

## 3. Failure analysis

| Finding | Evidence | Confidence / impact |
|---|---|---|
| Shared overlay bridge is a hard activation dependency; widgets are dormant if `icon_hover.dll` is not loaded or exports differ. | Runtime resolves only with `GetModuleHandleW` (does not load it), requires all five exports, then returns failure on acquire failure (`widget_host_runtime.cpp:327-334,745-755`). | High, high impact. Confirmed design; not proven to be current failure. Inspect plugin load order and runtime log. |
| Explorer restart/taskbar recreation is not handled by the widget host. | It stores a single HWND once, subclasses it, and removes subclass only on `WM_NCDESTROY`; no `TaskbarCreated` registration or reacquire call is present (`:720-728,776-801,696-698`). | High, high impact after Explorer restart. Existing core code has its own taskbar lifecycle, but widget runtime does not visibly consume it. |
| Only one taskbar/monitor is supported by this runtime. | Runtime has singular `taskbar`, `dpi`, taskbar rect and layout; Dpi is obtained from that HWND (`:55-56,720-726`). | High, medium/high impact for multi-monitor users. |
| Config schema disagrees about layout representation. | Default is array; settings fallback expects string; model parser reads JSON string (verify exact parser); GUI reads string (`default_config.jsonc:52`, `settings_page.cpp:1646-1656,2145-2148`, `widget_host_model.cpp:102-114`). | High, medium impact; likely ordering/default confusion. |
| Config change event may use inconsistent plugin name. | Listener filters for `widgets`, while plugin metadata name is `widget_host`; GUI reloads full config and config event data must be inspected (`widget_host.cpp:76-80`, runtime `:841-859`). | Medium. Depends on event producer contract; confirm `TE_ConfigChangedData.plugin_name` value. Full config may still be delivered with null name. |
| Redraw work is synchronized to a 1-second timer and redraws every widget; sysmon's own configured interval is not visibly polled by this host. | `kFrameIntervalMs=1000`; `RenderFrame` draws every layout item (`:30,535-570`); sysmon parses update interval (`sysmon_widget.cpp:45-46`) but this layer doesn't schedule per-widget updates. | High, likely wasted work and stale/over-frequent values depending widget implementation. |
| In-process C ABI is not crash isolation. | All widget DLLs are loaded with `LoadLibraryW`; callback guards use SEH (`:85-153,278-315`). SEH cannot recover from process termination, deadlocks, heap damage, or arbitrary hangs. | High, architectural risk; medium likelihood of present breakage. |
| Device/resource recovery is partial. | Generation mismatch destroys surfaces and reacquires shared resources, but failure just returns and later timer attempts may retry; taskbar HWND loss is separate (`:535-554`). | Medium. Device loss recovery exists, robust Explorer lifecycle does not. |
| Hit testing and rendering rely on the same HWND coordinate/DPI assumptions. | Input is intercepted at taskbar subclass and divided by captured dpi; render offsets are calculated from overlay/taskbar screen rects (`:520-532,577-579,386-413`). | Medium, likely issues with mixed-DPI/secondary taskbars or changed taskbar geometry. |
| Existing logs cannot isolate failure. | `Logs/taskbarengine.log` has only CoreManager/config watcher/IPC startup and shutdown entries from 2026-09-14, no widget host messages. | High. Do not infer runtime status from successful build. |

Confirmed findings are source-level behavior above. Assumptions are the likely failure ranking and expected runtime effects; confirm through targeted logs and visible/interactable UI evidence, not compilation alone.

## 4. API and project comparison

| Approach | Evidence and support | Benefits | Risks / fit |
|---|---|---|---|
| Windows Widgets provider (Windows App SDK) | Official Microsoft APIs provide `IWidgetProvider`, lifecycle, Adaptive Card updates and user actions; widgets display in the Widgets Board. Win32 providers require packaged apps and manifest extension registration ([provider overview](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/widget-providers), [overview](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/), [manifest](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/widget-provider-manifest)). | Supported system-hosted surface, system lifecycle and picker. | Not inline taskbar content; requires packaged provider and out-of-process COM activation. Cannot host arbitrary interactive widgets in this app's taskbar. Windows App SDK availability labels API version, not universal host support. |
| In-process DLL loaded by this host | Repository's present implementation (`widget_host_runtime.cpp:278-315`). | Fast callbacks, direct D2D, simple plugin deployment. | Crashes/hangs/ABI errors share process; private overlay contract and Explorer HWND subclass make stability dependent on internals. |
| Separate app-owned overlay/AppBar window | Microsoft Win32 windowing APIs are public; Windows App SDK supports desktop windowing across Windows 10 1809+ for the SDK family ([Windows App SDK FAQ](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-faq), [windowing overview](https://learn.microsoft.com/en-us/windows/apps/develop/ui/windowing-overview)). DirectComposition is a documented desktop composition API ([DirectComposition](https://learn.microsoft.com/en-us/windows/win32/directcomp/directcomposition-portal)). BetterBar source/docs show an app-owned taskbar replacement using Win32 AppBar, per-monitor DPI and separate panel/bar definitions ([project](https://github.com/Renbo2024/better-bar)). | Own HWND/process; easier restart, per-monitor lifecycle, crash isolation and input/focus/accessibility control. AppBar can reserve space. | A separate surface, not native taskbar child content; AppBar behavior/UX differs from shell taskbar and must test auto-hide/full-screen. |
| Child-window/taskbar embedding | Taskband open-source implementation finds `Shell_TrayWnd`/`Shell_SecondaryTrayWnd`, creates its own bar HWND and calls `embed_in_taskbar`; enumerates monitors ([main.rs](https://raw.githubusercontent.com/mnismi/taskband/main/src/main.rs), [taskbar.rs](https://raw.githubusercontent.com/mnismi/taskband/main/src/taskbar.rs)). | Empirical proof that projects implement this pattern; useful implementation reference for monitor detection and diagnostics. | This is project code, not a Microsoft support contract. Depends on Explorer window behavior and may break across Windows releases/taskbar redesigns. Treat as fragile compatibility mode, not supported API. |
| Inject/hook Explorer internals | This repository itself uses taskbar subclassing and an overlay from another injected plugin. | Can visually align with native taskbar and reuse its input. | Most coupled to Explorer lifetime and implementation. Avoid adding injection or internal visual-tree manipulation as the reliability fix. |

Microsoft documents `DirectComposition` as a desktop composition API; it does not document arbitrary insertion into Explorer's taskbar visual tree as a supported integration point. Windows App SDK broadly supports down to Windows 10 1809 for its components, but the Widgets provider host surface is documented as Windows 11 Widgets Board and has separate packaging/host constraints. Verify exact target OS/builds and installed runtime in the project's packaging before selecting SDK APIs.

## 5. Recommended architecture

- **Near-term stabilization:** retain current plug-in API and shared overlay only behind a lifecycle adapter. Add exact diagnostics for module path, discovered IDs, bridge exports, taskbar/overlay HWND identity, generation, render HRESULTs, and config event names. Ensure widget host can rebind after Explorer/taskbar recreation, and make initialization/config loading/type normalization deterministic. Keep only one owner responsible for overlay graphics resources.
- **Long-term boundary:** dedicated TaskbarEngine widget host process owns its own HWND(s), D2D/DComp devices, per-monitor layout, hit testing and accessibility. Main engine/settings communicate desired config over the existing IPC model or a versioned named-pipe protocol. Each widget is either a signed/trusted package/module running in the host (first migration) or a worker process for untrusted/third-party widgets. Host enforces timeouts, protocol version, bounds, restart policy and clean shutdown. No widget code runs inside Explorer.
- **Lifecycle:** enumerate monitor/taskbar topology; create/reposition one host surface per supported monitor; handle display/DPI/session changes; on Explorer restart, rediscover shell taskbars but preserve host process and recover geometry; on device loss rebuild graphics resources; on settings reload apply an atomic normalized config snapshot; disable removes visuals and stops per-widget work; shutdown drains callbacks and unloads only after worker/thread/resource teardown.
- **Plugin contract:** add ABI major/minor and structure-size fields, stable UTF-8 IDs, capabilities, per-widget instances, state serialization, explicit UI-thread/render-thread rules, callbacks for settings and topology changes, and ownership rules. Keep rendering inputs immutable per frame. For foreign native plugins, prefer process isolation because SEH is insufficient.
- **Configuration:** choose one canonical representation (recommend JSON array for ordered IDs), schema-version it, migrate the existing string form, preserve unknown widget settings, and distinguish engine-level host enabled from per-widget enabled. GUI builds order and toggles from a registry rather than a hard-coded three-ID list.
- **Surface support:** document two product modes: supported app-owned adjacent/AppBar host; best-effort inline taskbar compatibility integration. Windows Widgets Board provider is a separate optional integration only if users want a second, system-hosted widget surface.

## 6. Implementation plan

1. **Evidence and contract baseline (no behavior change):** inspect taskbar plugin loading order, `TE_ConfigChangedData`, overlay export implementation and package/install trees. Add/enable structured widget logs. Acceptance: a single startup log proves configured path, each DLL decision, selected taskbar/overlay HWNDs, bridge version, config snapshot version and active widget IDs; failure logs name the exact boundary.
2. **Normalize config and settings:** align `Config/default_config.jsonc`, `widget_host_model.cpp`, `settings_page.cpp`, `config_io.cpp`, and `widget_host.cpp` around a versioned array layout with a migration for current string values. Derive settings/order from discovered metadata. Acceptance: one edit survives app restart; settings UI and runtime report the same order and enabled IDs.
3. **Repair current lifecycle:** `widget_host_runtime.cpp`, `dcomp_overlay.*`, core taskbar lifecycle, and plugin loader. Add taskbar destroy/recreate detection/rebind, overlay generation recovery, display topology refresh, explicit per-monitor support policy, and cleanup ordering. Acceptance: Explorer restart restores visible/clickable widgets without restarting TaskbarEngine; device/display changes rebuild once without leaks or duplicate visuals.
4. **Make rendering/input deterministic:** widget ABI, host scheduler and built-ins under `Modules/widget_host/widgets/`. Honor per-widget update intervals/events; avoid redrawing static widgets; clamp measurements; define DPI unit and mouse/focus contract; add UI Automation/accessibility representation or accessible companion controls. Acceptance: clock advances, sysmon cadence matches setting, media updates on events, hit targets align at 100% and mixed DPI, keyboard/accessibility operation is available.
5. **Introduce process boundary:** new host executable and IPC protocol, migrate drawing/runtime ownership out of plugin or Explorer process. Keep compatibility adapter for existing DLLs only if all code remains outside Explorer. Acceptance: forced widget host termination does not terminate Explorer/engine; supervisor restarts host and restores config/state.
6. **Product support matrix and packaging:** update CMake, package/deploy/install scripts and docs. Define Windows 10/11/build/architecture/packaging matrix separately for supported adjacent host vs best-effort native taskbar placement. Acceptance: clean install contains runtime, widget modules and config; missing runtime/unsupported OS yields explicit diagnostic and graceful fallback.

## 7. Focused verification plan

Run only after implementation phases, not as broad suite:

1. **Discovery/render:** launch with one known widget and inspect structured discovery + successful surface draw/commit logs; visually verify pixels in correct taskbar-adjacent/inline location and that text updates. A successful DLL load or compile is insufficient.
2. **Interaction:** click a widget with a deterministic action and verify action result; hover tooltip and cursor; drag reorder and confirm visual movement plus persisted order. Check taskbar buttons/tray still receive input outside widget hit regions.
3. **Configuration:** change one widget setting and enable state in GUI; verify saved JSON, config event, runtime-applied snapshot and visible effect; relaunch to confirm persistence and unknown keys preserved.
4. **Recovery:** restart Explorer once while engine remains alive; verify new taskbar HWND is bound and widgets return. Then change display/DPI once (include a secondary monitor if supported) and verify correct scale and no stale duplicate surface.
5. **Isolation (new host architecture):** deliberately crash/terminate one widget worker/host and verify Explorer survives, host recovery occurs, and other widgets recover according to policy.

Avoid repeating model unit tests that only prove layout math; use them only if the corresponding model/config behavior changes.
